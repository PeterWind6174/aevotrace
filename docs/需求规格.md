# Aevotrace 需求规格

日期：2026-11-05。版本：0.2。状态：需求基线与实施建议；需求不因实验结果缩减。2026-11-07 的有界原型进展见 [当前状态](CURRENT_STATUS.md)，首版完成条件尚未满足。

本文区分用户已确认的产品要求和为推进首版提出的实施边界。未完成实验的方案不作为已具备的能力。

## 1. 已确认的产品定位

Aevotrace 是面向开发者的独立二进制转换工具。开发者提供已有程序和依赖，自行完成分析、必要的采集、转换与构建，得到可在目标平台运行的应用。

长期支持不同 CPU 架构与操作系统之间的组合。桌面系统与平台之间的转换优先，Switch 接入后置。通用性通过逐步增加经过验证的组合实现，不承诺从第一版自动支持全部组合。

## 2. 已确认的首版要求

| ID | 要求 |
| --- | --- |
| R01 | Windows x86-64 → macOS ARM64，目标为 Apple Silicon Mac |
| R02 | EXE、DLL 和资源即可作为输入，源码不是必要条件 |
| R03 | 有源码、符号或其他元数据时可以额外利用 |
| R04 | 第一版必须包含普通桌面 GUI 应用，不能以纯命令行样例替代首版交付 |
| R05 | 生成可以在 macOS 上独立启动的应用 |
| R06 | 正式运行 AOT 优先，允许 JIT 回退，将新发现内容用于下一轮离线构建 |
| R07 | 主要优化目标包括减少运行时编译和改善持续运行性能 |
| R08 | 同时提供兼容运行库模式和 macOS 原生接口/界面适配模式，由开发者选择 |
| R09 | 不承担驱动和内核等系统级组件的转换 |

## 3. 两种输出模式

模式是构建目标，默认按应用整体选择。首版不要求在同一进程中任意混用两套窗口系统。

| 方面 | `compat` | `native` |
| --- | --- | --- |
| 程序业务代码 | 提前生成 ARM64 代码，未覆盖部分允许 JIT | 共用 AOT/JIT 核心 |
| 系统接口 | 随包携带目标架构兼容实现，保留所支持的 Windows 接口语义 | 已支持接口通过适配调用 macOS 系统 API |
| GUI | 由兼容后端呈现所支持的 Windows 窗口/控件语义 | 已支持的窗口、控件及交互使用 AppKit 等原生框架实现 |
| 随包组件 | 兼容运行库、执行运行时、资源和依赖 | 执行运行时、ABI/回调桥接及必要的原生适配组件 |
| 未支持能力 | 明确报告依赖或运行时缺口 | 明确报告，不静默切换到兼容后端 |
| 验收 | 独立运行和行为验证 | 同等业务行为验证，额外核实界面确实使用原生后端 |

`native` 不是生成 macOS 风格图标或套一个原生启动器；它必须有实际的系统接口与 GUI 适配。对闭源二进制，不承诺自动恢复原始源码、原始控件设计意图或任意自绘界面的原生控件结构。

两种模式都保留必要的 Windows ABI 与应用可见语义。原生框架调用可能仍需包装和状态管理；能否消除某个适配层，由具体接口和程序决定。

## 4. 建议采用的首版应用边界

以下是实施建议，不是用户已经确认的完整兼容性清单。P0 必须将其落实为具体样例、应用与接口清单。

- 首先选择原生 C/C++、PE32+、普通 Win32 桌面程序。
- 覆盖窗口生命周期、消息派发、菜单、按钮、文本编辑、常用对话框、基础绘制及键鼠输入的明确子集。
- 覆盖应用所需的基础文件、内存、线程、同步、时间、模块装载与错误处理能力。
- 为 DLL 调用、GUI 回调、中文/Unicode、错误路径和重复启动准备样例。
- 不把纯自编样例运行成功描述为桌面软件普遍可用；首版还需固定第三方真实应用验证。

32 位 x86、.NET/WPF/WinForms、Electron/Chromium、复杂 COM/系统扩展、Direct3D、反作弊和任意并发自修改代码，先列为需要单独评估的能力。是否纳入其中某项取决于选定应用，不以“用户态”直接推导为已支持。

首版 GUI 工具外壳未被要求；建议先交付 CLI、配置文件及报告。这里的 GUI 要求是被转换应用具有可用 GUI。

## 5. 开发者使用流程

1. 导入 EXE、依赖 DLL、资源及可选的符号/提示。
2. 分析架构、模块、指令、系统接口和动态运行时依赖，得到能力报告。
3. 选择目标平台和 `compat` / `native`，处理报告中的缺口。
4. 执行准备场景，采集新代码、动态版本和必要 profile；可多轮增量补充。
5. 离线构建 AOT 代码、运行时、平台后端和应用包。
6. 在目标系统验证应用，查看 AOT 占比、JIT 回退原因和行为差异。
7. 将新发现输入下一轮构建；原始输入与上一个有效产物保留。

准备执行具体发生在 Windows 参考环境、目标平台执行环境还是两者配合，在 P0 选型时确定。SSH 只提供远程执行通道，不自动提供指令 Trace。

建议允许开发者通过项目配置声明模块、补充测试输入和适配插件；插件 API 在核心契约稳定后再冻结。

## 6. 独立应用的建议验收定义

- 包含 ARM64 Mach-O 执行入口及其所需的随包组件。
- 不要求终端用户安装 Aevotrace、编译工具链、Windows 虚拟机或单独配置兼容环境。
- 项目转换的主程序机器代码实际进入 AOT 产物；不能只把原 EXE 和已有运行器封装进 `.app` 就宣称完成转换。
- Aevotrace 路径不依赖 Rosetta 执行 x86 Host 组件；记录所有可执行依赖的架构。
- JIT 是允许的运行策略，不意味着必须在每次启动时重新编译已存在的代码。
- 应用资源、状态与增量缓存使用明确的可写目录；运行时不修改已签名应用包。
- 初期先验证本地开发签名和启动；正式分发签名、公证作为独立交付检查，不宣称自动满足 App Store 要求。

## 7. 正确性与性能

正确性包括业务输出、持久化文件、错误处理、线程同步和用户交互结果。两个 GUI 后端允许外观差异，必须记录有意保留的交互差异。

至少区分：

- AOT 执行 Guest 指令数占比；分发表命中率单独报告。
- 运行时 JIT 编译耗时、回退次数与原因。
- 首次启动、重复启动、持续 CPU 工作负载、GUI 事件响应。
- 离线构建时间、产物体积、加载与内存成本。
- 动态代码版本增长、跨次复用和缓存失效。

目标平台上以同一执行核心的 JIT-only 和持久化缓存 JIT 为对照。Windows 原生执行用于行为参考；不同硬件的耗时不能直接当作转换开销比例。性能阈值在建立基线后、正式比较前写入测试配置。

## 8. 首版完成条件

1. 同一组固定 Win32 GUI 测试程序，在 `compat` 和 `native` 下都可独立构建和运行。
2. 至少一个固定版本的真实桌面应用，在两种模式下完成预先定义的主要工作流；若支持对象暂不一致，必须分别发布范围，不能宣布完整首版达成。
3. 转换不依赖输入源码；带符号与去符号输入分别验证。
4. 使用独立于准备场景的输入验证正确回退，不能把单次录制固化成回放。
5. 代码修改、模块变化和缓存失配不会进入错误的 AOT 版本。
6. 提供可复现构建记录、双机验证证据、能力清单和性能原始数据。

## 9. 已知待决策项

- 真实应用及 GUI/API 子集，确认首版范围。
- 执行引擎、解码器、IR、JIT/AOT 生成方式、兼容实现的依赖与许可证。
- 最低 macOS/SDK、Windows 参考版本、首版 CPU 指令扩展。
- 准备执行的环境、追踪方式与输入格式。
- 原生适配自动化范围、手工适配接口和混合模式的后续边界。

这些决策进入 ADR，不能由不同 agent 分别假定。
