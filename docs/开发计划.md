# Aevotrace 开发计划

日期：2026-11-05。对应需求版本：0.2。状态：P0 已有执行核心及双 GUI 实验与独立 QA，代码已合入 main；P0 整体仍未通过。下文保留阶段计划，当前集成状态见 [合并记录](p0/INTEGRATION-20261105.md)。

## 1. 交付与实施原则

首版交付 Windows x64 → macOS ARM64 的独立转换工具，并提供 `compat` 和 `native` 两种输出。两个模式都必须完成 GUI 验收。内部阶段可以使用命令行小程序，但不能把它作为首版最终成果。

先解决执行核心、ABI、GUI 回调和可加载 AOT 的高风险问题，再扩展 API 和应用范围。两种 GUI 后端共用核心，避免各自实现一套 CPU 引擎。

不预先承诺完成日期或加速倍数。每个阶段只在验收证据完整后完成；后续估时依据实际任务吞吐和发现的问题修订。

## 2. 阶段与依赖

| 阶段 | 目标 | 可见交付 | 完成门槛 |
| --- | --- | --- | --- |
| P0 | 范围、选型和高风险验证 | ADR、应用清单、最小 spike、双机记录 | 关键路线有运行证据，无未解决的基础依赖或许可冲突 |
| P1 | 公共契约与双机构建测试 | ABI/格式 v0、构建骨架、Windows 参考样例 | 同版本源码可在双机复现参考结果 |
| P2 | x64 → ARM64 AOT/JIT 闭环 | 小程序转换、跨进程加载和未命中回退 | 独立输入、状态与副作用一致，确实执行生成的 ARM64 代码 |
| P3 | PE 应用与平台调用 | EXE/DLL 装载、基础接口、回调和线程 | 选定应用所需的核心平台语义可验证 |
| P4 | `compat` GUI 贯通 | 第一份兼容模式 `.app` | 固定 GUI 场景可用，包内执行链和依赖清楚 |
| P5 | `native` GUI 贯通 | 同源输入的原生模式 `.app` | 原生控件/系统适配真实生效，业务行为通过 |
| P6 | 真实应用、性能与首版交付 | 转换工具、双模式产物、报告与文档 | 满足需求规格的首版完成条件 |

主依赖为 P0 → P1 → P2 → P3 → P4/P5 → P6。P4 与 P5 在公共接口稳定后可并行；P0 就验证 GUI 关键点，不能到 P5 才发现路线不成立。

## 3. P0：必须先做的决策与实验

### P0-01 范围与真实应用

选择一个基础 Win32 GUI 自编测试族，以及至少两个真实应用候选，固定版本、二进制和资源哈希、来源及测试工作流。至少一个真实应用作为最终双模式共同验收对象。真实应用不必作为转换器的源码输入；许可允许的源码只供调查或参考。

列出输入框架、导入 DLL/API、指令扩展、动态装载、子进程、COM/托管运行时等依赖。将需求中的建议边界转成支持矩阵，记录暂不覆盖的能力。复杂框架若不适合首版，可换候选，但不能删掉 GUI 或双模式要求。

### P0-02 CPU 执行与离线产物 spike

对至少两个合理候选或两种实现路线比较：x64 语义、macOS ARM64 支持、可嵌入性、AOT 导出与重定位、JIT 回退、异常恢复、代码失效、构建成本和许可。

运行一个含分支、访存和间接调用的 x64 小程序，生成可在新进程加载的 ARM64 产物；强制一个未覆盖目标进入 JIT，再返回已编译代码。保留状态对比证据。只复用候选的 JIT 缓存不等于已证明所需 AOT 导出接口。

### P0-03 GUI 双后端 spike

同一 x64 测试程序创建窗口、按钮和文本框，经 Windows 风格回调修改业务状态。

- `compat`：验证选定兼容实现与转换执行核心可以互相调用。
- `native`：在 AppKit 主线程创建真实控件，将事件送回 Guest 回调，再正确返回 Host。
- 加测同步回调重入、模态交互和线程退出的最小情形。

P0 可以对少量已声明 API 使用手写适配，不可把 Host 原生重写版程序冒充转换成功。

### P0-04 平台 ABI 与依赖

核查 PE/Windows x64 调用约定、TLS、结构体布局、变参/回调、线程环境、错误状态和异常的需求。对候选依赖记录固定版本、许可证与集成方式；兼容运行库、CPU 引擎、解码器分别核查。现有非商业许可不自动解决第三方组合发布问题。

### P0-05 准备执行与双机流程

确定 Windows 参考执行与目标端采集各自负责什么。验证记录能够绑定输入模块、内容、场景和构建，不假设原生 Windows 采集结果能直接成为另一执行核心的内部 IR。

Windows SSH 会话工具链初始化、文件传输、工作目录、超时和退出码先打通。GUI 测试需要交互桌面时单列用户协作步骤。

### P0 验收产物

- ADR：执行引擎、编译路线、平台兼容路线、GUI 双模式、语言/构建系统、采集方案。
- 支持矩阵、真实应用选择和能力缺口清单。
- Spike 源码/命令/版本/结果，不只保留 agent 的结论。
- P1 任务分配及需要冻结的契约草案。

若某条路线失败，提交证据和替代方案，不通过改写需求宣布完成。两个模式保留为产品目标。

## 4. P1：公共契约和测试基础

建议以 C++ 和 C ABI 组织执行核心，macOS 适配使用 Objective-C++；工具编排可以采用 Python。最终语言选择由 P0 ADR 确定，不让不同 agent 各建一套工具链。

冻结以下 v0 契约：

1. GuestState、内存/权限/线程状态及退出原因。
2. AOT/JIT 调度、helper、Host↔Guest 调用和回调。
3. 模块身份、代码依赖、映射代次与失效事件。
4. trace/artifact manifest、平台后端能力声明、配置和版本兼容。
5. 双机测试结果格式、场景 ID、事件及文件比较规则。

交付双机构建入口、固定测试族、参考结果收集、报告脚本。自编测试代码可以保留源码，但测试转换输入必须能仅由 EXE/DLL 完成。

建议测试族：整数/分支/间接调用、文件读写、DLL 导入/导出、TLS、线程同步、窗口/控件、中文文本、回调、异常路径和动态代码。先实现阶段需要的子集，逐项记录覆盖。

## 5. P2：转换执行闭环

落实代码发现、有限指令语义、ARM64 代码生成、跨进程 AOT 加载、JIT 回退、重定位和持久化。

加入重复模板、嵌入常量、同址改写、解映射重分配和跨页依赖测试。新代码不能误命中旧产物；未实现的指令必须诊断，不能用返回零等占位行为让测试通过。

验收必须使用未参与准备采集的输入，并检查最终状态、输出、内存与文件副作用。诊断构建可细粒度计数，性能构建采用明确记录开销的统计方式。

## 6. P3：平台与程序装载

实现选定范围内 PE 映射、重定位、导入/导出、TLS、DLL 初始化、资源与延迟装载，以及真实应用需要的基础系统接口。

验证 Host 调用 Guest 回调、再从 Guest 调用平台接口的嵌套链，包含线程和错误处理。对动态查询或内部 NT 接口的依赖给出能力报告，不只检查静态导入表。

完成最小应用包骨架，并提前验证 JIT 内存规则、签名、可写缓存目录和无开发目录依赖。

## 7. P4/P5：双 GUI 后端

公共接口稳定后，两条实施任务可独立 worktree 并行，共用测试和事件语义。

| 场景 | 行为验收 | `native` 额外检查 |
| --- | --- | --- |
| 窗口/菜单 | 创建、缩放、关闭、菜单动作 | 原生窗口和菜单实际存在 |
| 按钮/编辑 | 回调、焦点、键盘、Unicode | 原生控件、输入与焦点行为 |
| 文件对话框 | 选择、取消、路径和错误 | 使用原生对话框 |
| 模态与线程 | 消息重入、工作线程通知、退出 | AppKit 主线程和回调调度正确 |
| 资源/绘制 | 选定字体、图标与绘制子集 | 明确区分原生控件和自绘内容 |

自动测试比较业务事件与结果，不以两种 UI 像素一致为条件。窗口外观、布局、焦点和模态交互须保留截图或人工核验记录。人工未完成时标为待验收。

## 8. P6：真实应用和性能

- 固定共同真实应用，完成预设主要工作流和独立验证输入。
- 同核心 JIT-only、持久化缓存 JIT、AOT Hybrid 分别测冷/热启动和持续运行。
- 两个输出模式分别报告，不把 UI 后端差异混入 CPU 转译收益。
- 测运行时编译、AOT 执行占比、CPU 工作负载、UI 响应、体积、内存和离线时间。
- 保存原始数据、重复次数、波动、环境和缓存状态；基于先前冻结的门槛判断结果。
- 在隔离环境验证产物独立启动，检查架构、动态库、签名、资源与用户数据目录。
- 完成开发者使用文档、能力与缺口清单、两种模式的选择说明和许可通知。

若只减少编译停顿而热身性能无改善，据实报告。若仍有未知正确性问题，不以平均性能良好抵消。

## 9. 第一批可派发任务

| 任务 | 负责人角色 | 依赖 | 完成物 |
| --- | --- | --- | --- |
| ENV-01 | qa | 无 | 双机工具链编译/运行 smoke；只读盘点已完成 |
| SCOPE-01 | binary + platform | 无 | 候选应用、API/框架矩阵、测试场景 |
| ENGINE-01 | compiler | SCOPE 初步范围 | 执行/AOT/JIT 候选比较与最小 spike |
| UI-01 | platform | 最小执行桥接 | compat/native 回调与窗口 spike |
| TRACE-01 | binary + compiler | 执行候选 | 准备采集和记录可移植性方案 |
| ADR-01 | coordinator | 上述证据 | 固定选型、接口 owner 和 P1 任务 |
| REVIEW-01 | reviewer | ADR 草稿和证据 | 对选型与需求覆盖的独立审查 |

初始建议一个主控、最多两个写代码的实施会话，加一个测试/审查角色按需工作。ABI 未冻结前，不开展大量相互依赖的实现任务。
