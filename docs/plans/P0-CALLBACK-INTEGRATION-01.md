# 下一轮计划：共同回调 ABI 与双 GUI 最小集成

日期：2026-11-05。状态：A/B/C 已执行；最终 HEAD 复跑与独立复核进行中。实际基线：main `c91a3f7`。

## 目标

将已分别验证的 ENGINE 与 UI 连成一条真实路径：用户/自动化操作控件 → Host GUI → ENGINE 执行 x64 Guest 回调 → Guest 调用明确支持的 Host 接口 → 更新界面 → 返回 Host。

同一个 x64 Guest 输入与同一执行桥分别驱动 `compat` 和 `native`，集成模式不使用 Unicorn。只完成最小回调链，不将其表述为完整 Windows GUI 应用支持。

## 为什么按这个顺序做

- ENGINE 当前从 COFF 函数生成 AOT/JIT，运行时和 probe 尚未提供 GUI 可复用的稳定调用入口。
- UI 当前通过 Unicorn 的 GuestMachine 调用函数、读写 Guest 内存和接收导入调用，不能只把对象名称换掉就视为核心集成。
- 先冻结两端的调用、退出、内存和错误契约，再实现薄桥，最后接界面，可避免编译器和平台任务各自定义不同 ABI。

## A：只冻结本轮需要的契约

- 入口/调用参数/返回值：首版只承诺当前核心可支持的整数和指针类型，写清 Windows x64 Guest 调用约定、栈对齐、shadow space 与可见寄存器状态。
- 生命周期：创建、装载、调用、读取结果、释放；同实例重复回调不遗留错误或破坏状态。
- Guest 地址与内存：保持 Guest 地址身份，经受检查的读写/映射接口访问，不把任意 Guest 值当 Host 裸指针。
- HostImport：用明确的 Guest 地址/ID 关联 Host helper；定义参数、返回和不支持时的行为，不持久化 Host 裸函数指针。
- 退出：正常 Guest 返回、Host 调用请求、未覆盖代码、内存/指令/API 错误分别表示；Host 异常不能跨 C/机器码边界传播。
- AOT/JIT：桥必须调用现有共享实现，不再复制一套 ORC dispatcher；ABI/结构尺寸需可检查，改动不得静默复用不匹配的旧产物。
- 范围：先单线程、AppKit 主线程上一层 Host→Guest→Host；任意 Guest 重入、线程/模态/完整消息泵明确不承诺。超出范围要诊断，不能死锁或假返回。

这是本轮试验契约，不是一次性冻结整个 P1 ABI/PE/TSO/异常系统。方案由 coordinator 汇总，compiler/platform 会签，reviewer 检查后再写桥接代码。

## B：先做没有 GUI 的共同执行桥

优先以薄 C ABI 导出当前核心，具体绑定方式由阶段 A 决定。核心仍可留在现有 spike 目录，本轮不做大型目录迁移或重构。

现有 runner、测试入口和新桥应尽量复用调度/helper/JIT 实现；抽取仅限必要公共部分。对无法统一的范围明确说明，不增加第三套复制的 JIT 路径。

先盘点旧 UI DLL 的指令/装载需求。若它需要大面积新增指令或 PE 能力，可新增一个更小的自编 x64 回调 fixture，保留旧 UI 测试作历史对照。允许明确的模块/入口/HostImport/重定位元数据或有边界的 fixture loader，但必须如实标注，不能宣称通用 EXE/DLL 转换。

Windows 参考程序必须执行同一份已固定哈希的 Guest 机器码输入；源码只用于生成和检查 fixture，Mac 不重新编译业务源码来替代机器码转换。

至少验证正常调用、重复调用、Host helper、未知 helper、故障返回、状态保留及一次真实 AOT/JIT 交接。结果和业务状态由 Guest 计算，Host 只负责适配。

## C：双 GUI 最小链路

复用已有两套后端。至少呈现一个窗口、输入框、按钮和结果区域。输入数值/文本中的本轮支持部分，经 Guest 回调计算后调用 Host helper 更新结果。

- 两个后端使用同一 Guest 输入哈希、入口和执行桥。
- `native` 使用真实 AppKit 控件且在主线程创建/更新；`compat` 走既有独立后端。
- 新的 ENGINE 集成模式不能加载或执行 Unicorn；旧 Unicorn 模式可作为明确标注的历史对照保留，禁止失败时静默回退。
- 使用至少三组不同输入/操作序列，保留一组不参与准备阶段的独立验证场景；不能把正确结果写死在 Python/ObjC++。
- 同一实例连续至少 100 次回调，验证状态和资源生命周期；这是稳定性 smoke，不是性能测量。
- 未支持 API、非法 Guest 内存、未支持重入显式失败；正常场景证据显示实际 AOT 与至少一次 JIT 编译/执行，错误场景不提交后续副作用。

自动操作和物理键鼠/输入法/焦点验收分开。可以用自动事件触发测试，但不能声称已经完成人工可用性检查。Windows 需要交互桌面时再给用户明确操作步骤。

1. 原 ENGINE 三组 ctest 不回归；原断言与 fixture 不削弱。

4. 可证明运行的是自建 ENGINE 的 ARM64 AOT/JIT，集成路径不依赖 Unicorn、Rosetta 或 Host 重写业务。
5. 模型/Max、会话 parent、目录、提交、命令、退出原因、截图与日志可复核。
6. 任一阶段未通过，保留已完成证据和具体缺口；不以重命名为完成。

不包含通用 PE loader、完整 Win32 消息泵、多线程/任意重入、模态覆盖、真实 7-Zip、通用 Trace 系统、代码版本失效、独立 .app、性能优化或产品发布。本轮必要的入口/调用诊断不是宣称 Trace 已完成。
